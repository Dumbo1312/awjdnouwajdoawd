# UEFITool performance presets
# ============================
#
# This is the file the Tweaks -> Performance presets dialog loads. It uses the
# same line format as patches/performance.txt and the same #!set directives,
# plus #!platform to group presets by chip and #!info for an entry that
# deliberately has nothing to apply.
#
# Line format:
#   FileGuid SectionType PatchType:FindPatternOrOffset:ReplacePattern
#
# Directives:
#   #!platform <name>  every set declared after this is grouped under <name>
#   #!set <id>         start a set
#   #!desc <text>      the name shown in the preset list
#   #!risk <word>      low, medium or high
#   #!note <text>      caveat shown when the preset is selected
#   #!info <text>      an entry with no patch lines; explains what to do instead
#
# All of them start with '#', so an older UEFIPatch reads this whole file as
# a plain patch file and ignores them.
#
# Read docs/risks-and-recovery.md before flashing anything made with these.
#
# ---------------------------------------------------------------------------
# Why the Intel group has patterns and the others do not
# ---------------------------------------------------------------------------
# A patch line is a byte pattern, and the compiler that built your firmware
# chose those bytes. A pattern therefore depends on the vendor, the board and
# often the exact BIOS build. The Intel sets below are the patterns that ship
# with upstream UEFITool, which are known to have worked on the platforms
# their comments name. Nothing here was invented: an invented pattern either
# silently matches nothing, or matches the wrong thing and bricks a board.
#
# For AMD and for graphics there are no upstream patterns at all, so those
# groups hold notes explaining the route that does work instead. Once you
# derive your own patterns with tools/msr-lock-scan.py and
# docs/pattern-cookbook.md, add them here with their own #!set and they show
# up in the dialog.

#----------------------------------------------------------------------------
#!set intel-cstate-unlock
#!desc Unlock CPU C-state control (MSR 0xE2)
#!risk medium
#!note Firmware sets a lock bit in MSR_PKG_CST_CONFIG_CONTROL and the register
#!note then stays read-only until the next reset, so no OS tool can change the
#!note package C-state limit. This stops it being locked. The image stays
#!note bootable; what changes is that a mistuned C-state limit set afterwards
#!note can hang or reboot the machine, which a CMOS clear undoes. Useful for
#!note frametime consistency work, not for average frame rate.
#----------------------------------------------------------------------------

#----------------------------------------------------------------------------
#!set intel-settings-note
#!desc Where the Intel frame rate actually is
#!info Power limits (PL1, PL2, IccMax, AC Loadline), the ring ratio, memory
#!info timings and Gear mode are setup menu settings, not byte patterns, and
#!info they are worth far more frame rate than anything on this list. If your
#!info board hides them, write the NVRAM variable instead of patching: dump the
#!info firmware, read the Setup module's IFR with IFRExtractor-RS to get the
#!info VarStore offset, then set it with setup_var.efi from a UEFI shell. No
#!info reflash, and a CMOS clear undoes it. See
#!info docs/bios-performance-guide.md, "Reaching settings the vendor hid".
#----------------------------------------------------------------------------


#============================================================================
#!platform AMD
#============================================================================

#----------------------------------------------------------------------------
#!set amd-no-patterns
#!desc No binary patches exist for AMD here
#!info Upstream UEFITool ships no patch patterns for AMD platform firmware,
#!info and none were invented for this project. There is nothing to click.
#!info This is not much of a loss: the AMD performance levers are all settings.
#!info Curve Optimizer and PBO limits (PPT, TDC, EDC) are usually the largest
#!info single gain after memory, and memory means EXPO or XMP on, with
#!info FCLK:UCLK:MCLK at 1:1 for as long as the controller allows it. On AM4,
#!info Power Supply Idle Control set to Typical Current Idle fixes a family of
#!info idle reboots and WHEA errors that look like a bad overclock.
#!info If your board hides any of these, write the NVRAM variable rather than
#!info patching: see docs/bios-performance-guide.md. If you do derive AMD
#!info patterns from your own dump with tools/msr-lock-scan.py, add them to
#!info this file under their own #!set and they will appear here.
#----------------------------------------------------------------------------


#============================================================================
#!platform Graphics
#============================================================================

#----------------------------------------------------------------------------
#!set gpu-resizable-bar-note
#!desc Resizable BAR is a setting, not a patch
#!info Resizable BAR is worth up to roughly 10-15% in some titles, which makes
#!info it one of the few real frame rate wins in firmware. It is a setup
#!info setting, not a byte pattern: turn on Resizable BAR and Above 4G
#!info Decoding, and turn CSM off. All three together, or it does nothing.
#!info On a board that hides them, the NVRAM variable route works; on some
#!info older boards the capability is genuinely absent from the firmware and no
#!info amount of patching adds it.
#----------------------------------------------------------------------------

#----------------------------------------------------------------------------
#!set gpu-vbios-note
#!desc GPU VBIOS is not a UEFI image
#!info A graphics card's own firmware is not an FFS image, so UEFITool can
#!info neither parse nor patch it and nothing here will touch it. Tuning a card
#!info means its power limit and clock offsets from the operating system, or a
#!info vendor specific VBIOS tool, both of which are outside this project.
#!info The GOP driver that does sit in system firmware only runs before the OS
#!info loads its own graphics driver, so patching it changes nothing in a game.
#----------------------------------------------------------------------------
